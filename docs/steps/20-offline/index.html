Offline Support

NetInfo connectivity detection, MMKV-persisted query cache, and mutations that queue offline and resume automatically on reconnect

feat(offline): add NetInfo detection, persisted query cache, and resumable optimistic mutations

What was set up

📡

Connectivity Detection

NetInfo feeds TanStack's global onlineManager. Every query and mutation in the app checks this one flag before attempting a fetch.

💾

Persisted Query Cache

PersistQueryClientProvider + a custom MMKV persister. Whole cache written to disk on every change, restored before first render on cold start.

⏸️

Paused Mutations

Creating/deleting a note while offline doesn't fail — it pauses. UI updates optimistically immediately, real request waits for connectivity.

🔁

Resume on Reconnect

Paused mutations — even ones restored from a previous session — automatically retry the moment the app is back online.

🔀

Reconciliation, Not Refetch

On success, the optimistic placeholder is swapped for the real server response in place — no blind invalidateQueries.

Two bugs found while wiring this up

① Mutation defaults registered too late

QueryClient.defaultMutationOptions() merges in a mutation's registered defaults once, then freezes the result. PersistQueryClientProvider restores mutations from disk in a useEffect that fires before any screen has mounted.

Registering setMutationDefaults lazily inside the useCreateNote/useDeleteNote hooks meant a mutation restored after an app restart got rebuilt with mutationFn: undefined — permanently. resumePausedMutations() would call it and silently no-op forever, no matter how many more reconnects happened.

Fix: moved setMutationDefaults to module scope in useNotes.ts. Since OfflineScreen is already eagerly imported by AppNavigator.tsx, this now runs during the static import phase — before restore ever fires.

② invalidateQueries silently erased writes

The original onSettled called invalidateQueries after every mutation — standard TanStack pattern. But JSONPlaceholder is a fake API that never actually persists writes: a refetch after "creating" a note returns the original seed data only, wiping the optimistic entry right back out. The mirror bug hit deletes too — a "deleted" note would reappear after the refetch.

Fix: replaced invalidate-refetch with direct cache reconciliation — onSuccess swaps the optimistic temp-id note for the real server response in place; onError rolls back to the pre-mutation snapshot. No refetch involved either way.
